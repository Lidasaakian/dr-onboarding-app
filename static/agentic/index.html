Audience: new team members who are comfortable with Python, a terminal, git and REST APIs.

How to use this learning path

  • Work through the days in order. Each module has the same shape: Goal → Read first → Hands-on lab (numbered steps) → Checkpoint → Check yourself.
  • Keep a personal learning log (template in Appendix D). Record every ID you create (Use Case, vector database, playground, deployment IDs). You will reuse them on later days.
  • Prefix every asset you create with your initials, for example ls-onb-, so shared environments stay tidy and you can clean up easily.
  • Placeholders used throughout: YOUR_DR_HOST is your DataRobot host name without https:// (for example app.datarobot.com, app.eu.datarobot.com, app.jp.datarobot.com, or your organization's own host); commands already include the https:// prefix. YOUR_API_TOKEN is your DataRobot API key. INITIALS is your prefix.
  • Items marked (Optional) or (Stretch) can be skipped if you are short on time or if the feature is not enabled in your environment.

The big picture: how the pieces fit

DataRobot organizes Agentic AI around a lifecycle: Build → Evaluate → Deploy → Monitor & govern. You build agents in code (usually from the Agentic Starter template with the DataRobot CLI), evaluate them in an agentic playground, register and deploy them through Registry, and monitor them in Console. RAG (retrieval-augmented generation) building blocks—vector databases, LLM blueprints and RAG playgrounds—live alongside agents and share the same evaluation, tracing and deployment machinery.

Lab 1.5 — Your first LLM gateway call

Why: every agent and blueprint in this path talks to an LLM. The gateway gives you one endpoint and one credential (your DataRobot key) for many models.

  1. List the models your org can use:

    dr llm list                      # table: ID, NAME, SOURCE (gateway | deployed), PROVIDER, MODEL, CONTEXT
dr llm list --output-format json

  1. Same list through the REST API:

    curl -s -H "Authorization: Bearer $DATAROBOT_API_TOKEN" \
  "$DATAROBOT_ENDPOINT/genai/llmgw/catalog/" | jq '[.data[] | select(.isActive == true) | .model]'

  1. Call two different models (Replace placeholders with real IDs from the MODEL column of dr llm list) with the OpenAI Python client. Create a virtual environment, then run:

    pip install openai datarobot
import os
from openai import OpenAI

client = OpenAI(
    base_url=os.environ["DATAROBOT_ENDPOINT"] + "/genai/llmgw",
    api_key=os.environ["DATAROBOT_API_TOKEN"],
)

# Pick two models from the MODEL column of `dr llm list`
for model in ["MODEL_FROM_LIST_1", "MODEL_FROM_LIST_2"]:
    r = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": "In one sentence, what is an AI agent?"}],
    )
    print(model, "->", r.choices[0].message.content)

  1. Try an unsupported model name (for example unsupported-provider/random-llm) and read the error.

Reference: Use the DataRobot LLM gateway (also shows LLMGatewayCatalog for filtering active/deprecated models) and dr llm-gateway command.

  1. Checkpoint: dr templates list works, dr llm list returns models, and your script prints two answers.

  1. Check yourself: In agent code, the gateway model name uses the format datarobot/<provider>/<model>. How does that differ from what you passed to the OpenAI client above, and why? (Hint: see “Model format for LLM gateway” in Configure LLM providers in code—LiteLLM uses the datarobot/ prefix to route.)

Day 2 — Module 2: Vector database and RAG playground (3 h)

Goal: understand retrieval-augmented generation in DataRobot by building a vector database and comparing LLM blueprints with and without it.

Explanation: an LLM only knows what it was trained on. RAG retrieves relevant chunks of your documents from a vector database and adds them to the prompt, so answers are grounded and cite sources. In DataRobot, an LLM blueprint captures the full recipe: base LLM, generation settings (temperature, max tokens…), system prompt, context state, and optionally a VDB with retrieval settings.

Read first

  • Vector database data sources — dataset requirements (document and document_file_path columns, ZIP or CSV).
  • Create a vector database — skim chunking and embedding settings.
  • Playground overview and Build LLM blueprints.

Dataset

Pirate resumes — a public DataRobot sample ZIP of resume documents, used in the official end-to-end GenAI walkthrough:

https://s3.amazonaws.com/datarobot_public_datasets/genai/pirate_resumes.zip

A ZIP is processed automatically into document + document_file_path columns. All files must sit at the root of the archive or in a single folder.

Lab 2.1 — Add the dataset

  1. Open your Use Case → add data → choose the import-from-URL option and paste the dataset URL above. (Alternative: download the ZIP and upload the local file.)

  1. Wait until processing finishes. Open the dataset and confirm it has document and document_file_path columns. Read two or three resumes so you know what questions to ask later.

Lab 2.2 — Build a resident vector database

  1. In the Use Case, click Add → Vector database → Create vector database.

  1. Provider: DataRobot (resident). Data source: the pirate resumes dataset.

  1. Embedding model: keep the DataRobot-provided default. Chunking: keep the default (recursive) method and note the chunk size and overlap values.

  1. Name it INITIALS-pirate-resumes-vdb and save. Wait for the build to complete; record the VDB ID.

  1. Open the VDB details and review what DataRobot reports (chunks, embedding model, versions).

Tip: For your own data later, a CSV with one text column renamed to document and a document_file_path column containing “fake” paths such as /kb/1234.txt works, plus up to 50 metadata columns for filtering.

Lab 2.3 — Create a RAG playground and compare two blueprints

  1. In the Use Case, open the Playgrounds tile → Add Playground → Add RAG playground. Rename it INITIALS-rag-playground.

  1. Blueprint A (no retrieval): Select LLM → pick a model available to you → Save. Set a system prompt:
    You are a recruiting assistant for a pirate crew. Answer concisely. If you do not know, say so.

  1. Copy Blueprint A to create Blueprint B, then on the Vector database tab select INITIALS-pirate-resumes-vdb. Save.

  1. Chat with each blueprint using these prompts:

    • “Which candidates have navigation experience? Name them.”
    • “Summarize the strongest candidate for a quartermaster role and cite the resume you used.”
    • “Who has leadership experience, and what evidence supports that?”

  1. Use the comparison view to send the same prompt to both blueprints side by side (compare LLM blueprints).

  1. For Blueprint B, open the citations under a response and review the retrieved chunks and scores (chatting and citations).

  1. Change one setting on Blueprint B (for example temperature to 0, or the context state between context-aware and no context) and repeat a prompt. Note the difference.

  1. Open the Tracing tile and find your prompts, the LLM used and the VDB used.

  1. Checkpoint: Blueprint A gives generic or “I don’t know” answers; Blueprint B names real candidates and shows citations.

  1. Check yourself: What does the context state setting change? Why does max completion tokens interact with the number of retrieved chunks?

Lab 5.2 — Add a local tool

  1. Add this tool class to myagent.py (from the docs’ Local datetime tool example):

    from datetime import datetime
from typing import Optional
from zoneinfo import ZoneInfo
from langchain.tools import BaseTool

class DateTimeTool(BaseTool):
    name: str = "datetime_tool"
    description: str = (
        "Returns the current date and time. Optionally accepts a timezone parameter as an IANA timezone "
        "string (e.g., 'America/New_York', 'Europe/London', 'Asia/Tokyo'). If no timezone is provided, "
        "returns local time.")

    def _run(self, timezone: Optional[str] = None) -> str:
        try:
            if timezone:
                current_time = datetime.now(ZoneInfo(timezone))
                return f"{current_time.strftime('%Y-%m-%d %H:%M:%S')} ({timezone})"
            return datetime.now().strftime("%Y-%m-%d %H:%M:%S")
        except Exception:
            return (f"Error: Invalid timezone '{timezone}'. "
                    "Please use a valid IANA timezone string (e.g., 'America/New_York', 'Europe/London').")

  1. Give it to the planner inside graph_factory, keeping the MCP/workflow tools already passed in:

    def graph_factory(llm, tools, verbose=False):
    datetime_tool = DateTimeTool()
    all_tools = [datetime_tool] + list(tools)
    planner = create_agent(
        llm,
        tools=all_tools,
        system_prompt=make_system_prompt("...your planner prompt..."),
        name="planner_agent",
        debug=verbose,
    )
    ...

  1. Test: task agent:cli START_DEV=1 -- execute --user_prompt 'What time is it in Tokyo and in Dublin right now? Then write two sentences about working across those time zones.'

  1. In the Traces tab, find the datetime_tool span and its arguments. Try an invalid timezone and see how the agent recovers from the tool’s error message.

Explanation: tools can live in three places. Local tools (like this one) run inside the agent process. Deployed global tools (Registry models prefixed [Tool], such as Search Data Registry or Summarize DataFrame) scale independently and get Console monitoring—see Deploy agentic tools. MCP tools are served by an MCP server and discovered at runtime (Lab 5.4).

    def build_prompt_template() -> ChatPromptTemplate:

   version = template.get_latest_version()

Lab 7.1 — Deploy with the CLI

dr run deploy

This builds the custom model and creates a production deployment plus the application (several minutes). Copy these outputs into your log: AGENT_DEPLOYMENT_ID, the Agent Deployment Chat Endpoint (…/api/v2/deployments/ID/chat/completions), the Agentic Starter application URL, and the MCP server deployment ID and endpoint.

Explanation: the CLI path does, in code, what the UI path does by hand: Workshop (assemble) → Register a workflow (Registry → Models, Agentic workflow tab, status Building → Ready for deployment) → Deploy (Console). Lab 7.3 — Call the deployed agent

  1. Console → Deployed workloads → Agentic Workflow tab → your deployment → Predictions → Prediction API: choose Real time, Python, and copy the snippet.

  1. Or use the OpenAI client (from the docs):

    import os
from openai import OpenAI

DEPLOYMENT_ID = "YOUR_AGENT_DEPLOYMENT_ID"

    base_url=f"{os.environ['DATAROBOT_ENDPOINT']}/deployments/{DEPLOYMENT_ID}/",
    api_key=os.environ["DATAROBOT_API_TOKEN"],
    _strict_response_validation=False,
)
r = client.chat.completions.create(
    model="datarobot-deployed-llm",
    messages=[{"role": "user", "content": "What time is it in Singapore? Then write a two-line status update."}],
)
print(r.choices[0].message.content)

  1. Open the deployed application URL and chat through the UI too.

Lab 7.5 — Guardrails (read; hands-on if enabled)
